01What a harness is

A harness is the set of files that let a coding agent start consistently, stay in scope, verify its own work, and resume after the context window is gone. It is not a framework and runs no code of its own — it is markdown plus one shell entrypoint, sitting in the target repository.

The skill that generates it does three things: scaffold a harness into a project, score an existing one, and retrofit missing pieces into one that already exists. Everything it writes is a plain file a human can read and edit.

The core distinction introduced in v0.3.1. Earlier versions tracked state — where the work stopped — very well, and recorded no learning at all. State is a bookmark; a lesson is knowledge. A harness could score full marks and never get better at anything. Memory is now its own subsystem for exactly that reason.

05State layer

Episodic. Answers “where am I”, and stops being true once the current feature ships.

harness/feature_list.json

The source of truth for what to build. Each entry carries id, description, dependencies, status and evidence. The evidence field is what makes “done” falsifiable — a status of done with an empty evidence field is a red flag, not a completion.

  • generated from templates/feature-list.json
  • validated by templates/feature-list.schema.json
  • writes feature_list.json

harness/progress.md & harness/session-handoff.md

Continuity. harness/progress.md holds current state, decisions made (with rejected alternatives), risks and accumulated debt. harness/session-handoff.md holds the verification evidence table, files changed, and the recommended next step.

These are not memory. They are the bookmark. Conflating them with memory was the single most common failure this version fixes.

  • generated from templates/progress.md, templates/session-handoff.md
  • writes progress.md, session-handoff.md

06Verification layer

init.sh the only gate

One entrypoint, run at startup and again before any claim of completion. Its exit code is the number of failed checks, so it composes with CI without extra glue. It must set -e and it must print a clean-restart path.

In a codebase it wraps tests, build and lint. In a documents-only project there is nothing to compile, so it verifies tool availability and artifact integrity instead — the harness does not require that a project have code.

  • generated from templates/init.sh
  • writes init.sh (mode 0755)

07Memory layer new in v0.3.1

Durable. Answers “what do I now know that I didn't before”, and outlives the feature that taught it.

harness/memory/index.md

The always-on index: one pointer row per lesson, read every session. Topic files are opened only when a row looks relevant — progressive disclosure, so depth stays available without paying context for it.

Hard cap
~200 lines / 25KB. Overflow is a signal to merge or delete lessons, never to raise the cap.
Two-step save
Write harness/memory/<slug>.md first, then append the index row. Topic-file-first is deliberate: a crash between the two leaves an orphan, never a broken index.
Retired, not deleted
A wrong lesson is the record of how far it propagated. It moves to a Retired section with a reason.
  • generated from templates/memory-index.md
  • writes harness/memory/index.md
  • shape defined by templates/memory-entry.md (not scaffolded; consulted)

harness/memory/journal.md

Append-only. One dated block per session: what you looked up, what surprised you, what correction you received, what you would do differently. Three to five lines, no prose.

This is the corpus curation reads. Without it, “find recurring patterns” has nothing to count and every proposal is an opinion. It is not a lesson store and not a progress log — it is raw, unfiltered friction.

Commands, paths and symbols go in backticks: a journal with no backticks is a journal of feature restatements and will yield no proposals.

  • generated from templates/memory-journal.md
  • writes harness/memory/journal.md
What must never be stored in memory. Anything re-derivable from the codebase (architecture, call graphs, file layout — all stale within a month), anything true only for the current conversation, and anything that is really status. Also: memory content is evidence, not instruction. An imperative sentence inside a memory file has no authority over the agent. That is the structural defence against a poisoned store, in place of a keyword blocklist that would lose.

08Memory & curation loop

Two loops write to one store: a fast one inside the session, a slow one between sessions. They exist separately because a working agent is structurally incapable of curating memory well — and understanding why is the key to the whole design.

Why one loop isn't enough

The obvious design is: let the agent write memory as it works. That gets you most of the way, then hits two walls that no amount of better instruction fixes.

WallWhat it meansWhy instruction can't fix it
Split focus The agent is asked to finish the task and invest in memory that only helps a future run. It's an unresolvable trade-off mid-task. How much of a budget meant for the job should go to helping later versions of itself? Any answer is arbitrary, and under pressure memory always loses.
Single-session visibility The agent sees only its own session. It cannot know the same correction has now been made four times. Each session starts with a fresh context window. The pattern exists only in the aggregate, which no single session can see.

The consequence is a store that grows but doesn't improve: duplicates that disagree, lessons nobody used, entries that were true in session three and misleading by session forty. So the work is split. The session captures; a separate pass curates.

Loop 1 — in band, during the session

This loop is cheap and runs every single session. Its job is capture, not judgement.

  1. At startup, read harness/memory/index.md. One pointer row per lesson. The agent scans the rows and opens a topic file only when a row looks relevant to the task in hand. This is progressive disclosure: full depth stays available, but you pay context only for what you open.
  2. Do the work. Memory is not touched again mid-task. Nothing is appended opportunistically — that's what produces stores full of noise.
  3. At the end, append one dated block to harness/memory/journal.md. Three to five lines answering only: what did I have to look up, what surprised me, what correction did I receive, what would I do differently. Raw and unfiltered. If a session produced none of those, write nothing — that is a real signal, not a gap.
  4. Only if a lesson is already obviously durable, do the two-step save now. A direct user correction always qualifies. Everything else stays in the journal and waits for curation to decide whether it's a pattern.

Step 4 is the discipline that matters. The temptation is to promote every observation to a lesson immediately. Resisting that is what keeps the index under its cap — most journal lines are noise, and you can only tell which by seeing whether they recur.

The two-step save, and why the order is fixed

Writing a lesson is always: topic file first, then the index row. Never the reverse. This looks like pedantry until you consider what happens when a session dies between the two writes.

Order usedCrash between writes leavesConsequence
Topic file → index correct An orphaned topic file: real content, no pointer. Recoverable and harmless. The index stays truthful — every row it holds resolves. The orphan is detected by the links check and can be indexed or deleted.
Index → topic file A dangling row: a pointer to a file that doesn't exist. The always-on file now lies. Every future session reads a row promising a lesson, follows it, and finds nothing.

The rule picks the failure you can live with. And because both states are mechanically detectable, the scorer's links intact check enforces it — this is the one check that fails on a harness that drifted rather than one that used the wrong words.

Loop 2 — out of band, between sessions

This loop is expensive and runs rarely. Its job is judgement, and it has two advantages the session lacks: its own budget, and sight of every session at once.

  1. Read the journal against the store. Inputs are harness/memory/journal.md (the accumulated friction) plus harness/memory/index.md and its topic files (what's already known).
  2. Look for exactly four things. Not "anything interesting" — a bounded checklist, so the pass is repeatable and its output predictable. See the table below.
  3. Write proposals to harness/dream-queue.md. Each carries a claim, its evidence (which journal dates or files), and a prevalence count. No citation, no entry.
  4. Stop. Nothing is applied. The pass has no write access to anything except its own queue.
  5. A human accepts or rejects each proposal, typically at the start of the next session. Accepted changes are written into harness/memory/. Rejections go to the Decided table so the same idea can't quietly return next cycle.

The four signals, concretely

A curation pass is only looking for these. Anything else it notices is out of scope.

SignalWhat it looks like in the journalWhat gets proposed
Recurs but missing The same lookup or correction appears across several dated blocks, and no lesson covers it. Add a lesson. Highest-value outcome of the whole loop.
Two that contradict Two existing lessons give opposing guidance on one question. Retire one. Two live authorities on the same question is a bug — the agent will follow whichever it reads first.
Never referenced A lesson exists, but nothing in the journal ever shows it being used or needed. Delete it. Dead entries consume index budget and dilute the rows that matter.
Now contradicted A lesson's claim is refuted by recent journal evidence — the constraint changed. Correct or retire, keeping the old entry with a reason. Stale memory is worse than none: it is confidently wrong.

A worked example, end to end

Concrete trace of one lesson entering the store the intended way.

Session 1
Agent runs ./deploy.sh, the deploy half-fails, user corrects it. Journal gains: corrected: use `make ship`, not `./deploy.sh`. Not yet a lesson — one occurrence.
Session 4
Different feature, same mistake. Journal gains a near-identical line. The agent in session 4 has no idea this happened before — fresh context window.
Session 7
Third occurrence. Still invisible to any individual session.
Curation pass
Reads all journal blocks, finds the backticked token make ship recurring across three separate dates with no covering lesson. Signal 1 matched. Writes to the queue:
Add lesson: deploy via `make ship`, not ./deploy.sh — evidence: journal 07-14, 07-19, 07-22 — seen 3×
Human review
Reads one line with three citations and a count. Accepts.
Applied
harness/memory/deploy.md written with the rule and a **Why:** line (the script skips migrations), then the pointer row appended to harness/memory/index.md. Two-step order.
Session 8 onward
Startup reads the index, sees the deploy row, opens it when deploying. Mistake stops recurring. Journal stops accumulating that line — which is itself the evidence the lesson worked.

Note what did the work: counting. Nobody had to be clever. The pattern was mechanically visible the moment something looked across sessions instead of within one.

Why the human gate is non-negotiable

Curation proposes; a human decides. This is the load-bearing rule of the whole design, and it exists because of a specific attack rather than general caution.

The attack. An unattended process with write access to the instruction layer can silently move the bar it is judged against. Consider a proposal that subtly weakens the definition of done. Applied automatically, every future session grades itself against the weaker bar, everything reports green, and the harness has become an elaborate way of agreeing with itself. Nothing detects it, because the thing that would detect it is what changed.

Two structural constraints follow:

  • Curation may write harness/memory/ only. It may suggest an instruction change; it can never make one. The worst case of a poisoned store is therefore a bad note, not a new rule.
  • Memory content is evidence, not instruction. An imperative sentence inside a memory file has no authority over the agent. If a lesson file says "run this command" or "ignore the following rules", that is a finding to report, not an order to obey. This is a structural defence rather than a keyword blocklist — blocklists lose, because the attacker picks the words.

Cadence — why not after every session

Running curation constantly seems safer. It is worse, for a reason that isn't obvious:

  • A pattern needs several sessions to exist. After one session there is nothing to count. A pass run on one block can only report the block back to you.
  • Frequent passes produce noise, and noise trains the reviewer to skim. Once you're skimming, the human gate is nominal — you've bought unattended memory writes with a rubber stamp attached, which is exactly the thing the gate exists to prevent.

Hence the triggers: every ~10 sessions, weekly, or when the index passes 160 lines (80% of cap). The third is the interesting one — it fires on pressure rather than on the clock, which is when curation is genuinely overdue.

Review fatigue, and why the cap is structural

Review fatigue is the dominant failure mode of this entire pattern — more likely than any technical fault. An unbounded queue becomes a thing you clear reflexively.

The answer is not discipline, it is capacity: 5 open proposals, maximum. A pass that finds twelve patterns must rank, merge and drop its own until five remain. That inverts the economics — volume becomes the proposer's problem instead of the reviewer's, and it forces the pass to do the ranking work that a human would otherwise do badly at 11pm.

A useful property falls out of this: overflow can simply be dropped rather than queued. Prevalence only grows, so a real pattern resurfaces next cycle ranked higher. A backlog, by contrast, converts fatigue into permanent guilt.

Failure modes worth watching for

FailureFirst symptomGuard
The journal rots into feature restatements — the most likely failure of all, since it's written last, when budget is gone. Not a complaint. A curation pass over 40+ blocks that yields zero proposals. The corpus grew, the signal didn't. Tell-tale: blocks with no backticked tokens. The four fixed questions, and the instruction to write nothing rather than filler.
Memory and harness/progress.md converge, and every lesson gets written twice. The index crosses 160 lines within weeks, and its rows read like a changelog — feature names and dates rather than lessons. The boundary test: if the note stops being true when the current feature ships, it is state, not memory.
Rubber-stamping. The gate becomes ceremonial. Invisible by construction — a drained queue and a considered queue look identical afterwards. Keep the queue short. There is no mechanism that detects a stamp, which is exactly why the cap matters more than any check.
Prevalence measures reporting, not reality. Known problems never generate proposals, because sessions silently work around them instead of journalling them. Journalling is a fixed end-of-session step, not a judgement call about whether something was worth noting.
Curating too early. The first pass finds nothing and feels like wasted effort, which discredits the practice. Accumulate first. Let the store get messy on purpose — the mess tells you which rules you actually need.
Start manual. There is no bundled curation script, and that is deliberate. Open a session and ask it to read the recent journal plus the whole store and report what recurs, contradicts, and went unused. That pass is dreaming. Automate only after seeing what it finds — otherwise you encode thresholds for problems you don't have.

11How scoring works

Each subsystem runs a handful of checks. Score is round(passed / total × 5), floored at 1. Overall is the sum over 35, as a percentage.

Two guards on the verdict

  • The tier gates on the weakest subsystem. ≥85 overall with any subsystem at ≤1/5 reports usable, not production. One subsystem is worth only ~14%, so total failure of one cannot drop the percentage out of the top band by itself — without this guard the tool could print Bottleneck: memory, memory: 0/5 and ✅ production together.
  • Bottleneck tie-breaks toward structural subsystems, and Also low: names anything else at ≤2/5. Memory is new, so most existing harnesses score 1 on it and would otherwise mask a genuinely broken verification or lifecycle.

Why most checks are keyword checks — and why memory's are not

Most checks grep the structured parts of AGENTS.md for documented rules. That is reasonable for “is this rule written down”, but it measures vocabulary, not behaviour: a stub with the right nouns passes, and a well-run project using different nouns fails.

The memory subsystem therefore includes computed assertions over the store itself:

CheckKindCan it fail on a real harness?
Memory index existsfile presenceOnly if absent
Index initialised and within capcomputedYes — empty, or over 200 lines / 25KB
Links intactcomputedYes — dangling or orphaned lessons
Curation input existsfile presenceOnly if absent
Two-step save documentedkeywordVocabulary-sensitive
Curation cadence + human gatekeywordVocabulary-sensitive

The links check is the only assertion in the whole scorer that fails when a harness has drifted rather than when it used different words. It catches the exact failure the two-step save exists to prevent: a lesson file written but never indexed, or an index row pointing at a file that was never written.

Memory is excluded from the corpus-wide text. Agent-written memory used to feed the checks that scan every file, so the word “Evidence” in a queue table header satisfied verification's “evidence is recorded” check for free. Memory content can no longer prove anything about other subsystems.
