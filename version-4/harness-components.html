harness-creator · version 4 (0.4.0)

Harness Components

Every system in the harness: what it is for, which files it owns, what it reads and writes, what changing it affects, and how it is scored. One system per chapter.

00What a harness is

A harness is the set of files that let a coding agent start consistently, stay in scope, verify its own work, and resume after the context window is gone. It is not a framework and runs no code of its own — it is markdown plus one shell entrypoint, sitting in the target repository.

The skill that generates it does three things: scaffold a harness into a project, score an existing one, and retrofit what is missing. Everything it writes is a plain file a human can read and edit.

The organising idea. Every check asks one question: would a fresh agent, with no memory of the last session, do the right thing? A harness scores well when the answer is yes without a human in the loop.

01Install layout & directory structure

A scaffold puts three files in the project root and everything else under harness/. The three at the root are not a style choice — each is read from there by something outside this harness.

What a scaffolded project looks like

your-project/
├── AGENTS.md          ← instruction file; the cross-tool convention
├── CLAUDE.md          ← one line, points at AGENTS.md
├── init.sh            ← verification entrypoint, invoked as ./init.sh
└── harness/
    ├── feature_list.json      state · source of truth for features
    ├── progress.md            state · session continuity log
    ├── session-handoff.md     lifecycle · structured end-of-session handoff
    ├── open-work.md           scope · seen but declined, recruitable
    ├── dream-queue.md         curation · proposals awaiting a human   (optional)
    ├── environment.md         verification · declared preconditions   (optional)
    └── memory/
        ├── index.md           bounded always-on index of lessons
        ├── journal.md         append-only friction log; curation input
        ├── graveyard.md       rejected routes + expiry conditions     (optional)
        ├── <slug>.md          one lesson per file
        └── audit-log.jsonl    append-only score history               (optional)

Why these three stay at the root

AGENTS.md is the convention every other agent tool reads from the repo root. CLAUDE.md points at it, and Claude Code only looks in the root. init.sh is invoked as ./init.sh by docs, humans and CI.

Path convention

Every path is written relative to the project root — in every file, including files already inside harness/. One rule, no depth arithmetic. The sole exception is link targets inside harness/memory/index.md, which stay sibling-relative.

Older harnesses still work. A harness created before harness/ existed keeps its files at the root and scores identically. loadHarnessFiles() probes both locations and returns canonical keys either way, so the scorer never learns the layout. detectHarnessLayout() ensures a newly created file joins the layout a project already uses, rather than splitting it across two.

02The systems at a glance

Seven scored systems, plus curation — machinery attached to memory rather than a scored system of its own. One line each; a chapter each after this.

SystemIn one lineOwnsChecks
Instructions structuralTells the agent how to start, what the rules are, and when it may say "done".AGENTS.md / CLAUDE.md5
State structuralRecords what exists, what is in flight, and what evidence was produced.feature_list.json, progress.md5
Verification structuralMakes "done" falsifiable by running something that can fail.init.sh, environment.md8
Scope structuralStops one task becoming five, and gives declined work somewhere to live.open-work.md, feature fields6
Lifecycle structuralMakes the next session restartable without asking a human what happened.session-handoff.md, init.sh5
Memory learningKeeps what was learned, as distinct from where the work stopped.memory/7
Behavioral policyGoverns how code gets written: minimal, surgical, test-first, safe.sections in AGENTS.md8
Curation unscoredBetween sessions, proposes what memory should gain, merge or retire — never applies it.dream-queue.md—

44 checks across 7 systems, each system scored out of 5, totalling 35 and reported as a percentage.

Memory is not state. progress.md and feature_list.json record where the work stopped — a bookmark. Memory records what is now known that wasn't before — a lesson. A harness can track state perfectly and never learn anything. That distinction is why memory is its own system.

03Session flow

Where each system engages during a single session.

1 · StartRead AGENTS.md, run ./init.sh, read feature_list.json, scan open-work.md, read memory/index.md.
2 · OrientState the task in one line. Name the scope boundary. Surface any open dream-queue proposals to the human.
3 · WorkOne feature. Test first. Surgical edits. Anything noticed but out of scope goes to open-work.md.
4 · Verify./init.sh must pass. Evidence recorded against the feature.
5 · CloseUpdate progress.md and feature_list.json, append to memory/journal.md, fill session-handoff.md.
6 · BetweenCuration reads the journal and writes proposals. A human accepts or rejects. Never inside a session.

04Instructions

The always-on file. Everything else is reachable from it, and most other systems are partly documented here rather than living somewhere separate.

Purpose

Give a fresh agent a deterministic startup path and an unambiguous definition of done, so behaviour does not depend on what happened to be in the last context window.

Impacts / updates

Read by every other system's keyword checks — scope, lifecycle, behavioral and memory are all partly scored on their sections here. Written by create-harness, patched by enrich-harness. Editing it can move four systems' scores at once.

Components

SectionRoleScored by
Startup WorkflowOrdered steps before any code is writteninstructions
Required ArtifactsWhich files exist, split into required and optionalinstructions
Working RulesOne feature at a time, stay in scope, leave cleanscope
Definition of DoneThe completion gate, test-firstinstructions, scope
Verification CommandsWhat to run, and that ./init.sh is the entryinstructions, verification
End of SessionClosing procedurelifecycle
Memory · CurationTwo-step save, cadence, propose-never-applymemory

Checks (5)

  • Agent instruction file exists
  • Startup workflow documented
  • Definition of done documented
  • Verification commands discoverable
  • State artifacts routed from instructions

05State

What exists, what is in flight, what was proven. The bookmark a resuming session reads first.

Purpose

Survive the context window. A session that ends abruptly should cost minutes to resume, not a re-investigation of the codebase.

Impacts / updates

Written by the agent every session and by create-harness / enrich-harness. feature_list.json is also read by scope for dependencies and status. progress.md doubles as the fallback for the lifecycle restart-marker check when no handoff exists.

Components

ArtifactHoldsWritten when
harness/feature_list.json requiredid, name, description, dependencies, status, evidenceA feature starts, changes status, or completes
harness/progress.md requiredCurrent state, done / in progress / next with per-step verification, blockers, decisionsContinuously, and at session end
harness/feature_list.schema.json referenceJSON Schema for the tracker — id pattern, status enum, required fieldsNot scaffolded; copy it to validate in CI

Checks (5)

  • Feature tracker exists
  • Feature tracker is valid and has feature fields
  • Progress log exists
  • Progress log supports restart
  • Handoff captures blockers/files/next step

06Verification

The system that makes "done" mean something. The largest check count of any system, because it is the one most easily faked.

Purpose

Give the agent something that can fail, and make running it the precondition for claiming completion.

Impacts / updates

init.sh is also the lifecycle startup script, so it is scored twice. It reads harness/environment.md before anything else. mutate-gate.mjs deliberately breaks it to test whether the gate notices. Two checks read init + agents, so documenting commands in AGENTS.md satisfies them legitimately.

Components

ArtifactRole
init.sh requiredSingle entrypoint. Fails fast. Runs the environment contract first, then the project's own checks.
harness/environment.md optionalPreconditions as table rows whose Check cell is a shell command. Exit code is the verdict — no output parsing.

The environment contract

A missing tool is not a failing test. Conflating the two sends the next session debugging code that was never broken, so the contract reports separately and exits with an explicit this is the machine, not the code message. The loop sits inside an if so a failing requirement does not abort the run — four unmet requirements surface together rather than one per re-run.

The block lives in two places by necessity. create-harness.mjs generates init.sh and never copies templates/init.sh, so a change made only to the template would never reach a scaffolded project. A self-check now asserts every shipped init.sh reads harness/environment.md.

Checks (8)

  • Verification entrypoint exists
  • Verification fails fast
  • Test command documented
  • Static/build check documented
  • Verification evidence is recorded
  • Entrypoint actually runs a command
  • Declared environment preconditions are checked by the entrypoint
  • Gate demonstrably catches known breakage --mutate only

07Scope

Keeps one task from becoming five, and gives everything the agent noticed-but-didn't-do a place to live instead of being silently dropped or silently built.

Purpose

Bound the diff. An agent that fixes adjacent things while it is "in there" produces changes nobody asked for and nobody reviews properly.

Impacts / updates

Mostly documented in AGENTS.md Working Rules, and partly read from feature_list.json (dependencies, status). open-work.md is the only file it owns outright, and it is always-on context — bounded by attention, not disk.

Components

Artifact / ruleRole
harness/open-work.md requiredOne line per observation with a reason code. Recruitable — a later session can pick up a cheap-parallel-win that fits the task in front of it.
feature_list.json dependenciesMakes ordering explicit, so "next" is derivable rather than guessed
Working Rules in AGENTS.mdOne feature at a time; stay in scope; no bonus surface

Checks (6)

  • One-feature-at-a-time rule exists
  • Feature dependencies are tracked
  • Feature status is explicit
  • Scope boundary documented
  • Completion gate limits scope closure
  • Recruitable open-work surface exists

08Lifecycle

The bootstrap and shutdown procedure. Turns a repository into something a stranger can pick up cold.

Purpose

Make every session start the same way and end in a state the next one can resume from without a handover conversation.

Impacts / updates

Shares init.sh with verification and progress.md with state — its restart-marker check reads progress + handoff together, so either can satisfy it. Its end-of-session procedure is what causes memory/journal.md to be appended, making it the trigger for the whole curation pipeline.

Components

ArtifactRole
init.sh requiredThe one documented way to start; also the verification gate
harness/session-handoff.md requiredObjective, evidence table, files changed, decisions, blockers, next step. The file must exist; filling it in is what is optional for small sessions.
End of Session in AGENTS.mdThe closing checklist itself

Checks (5)

  • Startup script exists
  • End-of-session procedure exists
  • Session handoff template exists
  • Session restart markers exist
  • Clean restart path documented

09Memory since v0.3.1

What is now known that wasn't before. Earlier versions tracked state very well and recorded no learning at all — a harness could score full marks and never get better at anything.

Purpose

Stop re-paying for the same discovery. A lesson that would have saved time on a different feature belongs here; anything that stops being true when the current feature ships belongs in progress.md.

Impacts / updates

Written by the agent at session end, read at session start. memory/index.md is always-on context, so its size is a budget question, not a storage one. Three checks inspect the store itself rather than prose about it, so they cannot be satisfied by vocabulary in AGENTS.md. Consumed by curation.

Components

ArtifactRoleBound
memory/index.md requiredOne line per lesson, read every session; topic files opened only when a line looks relevant~200 lines / 25KB
memory/journal.md requiredAppend-only per-session friction log. Not a lesson store — it is the raw corpus curation readsappend-only
memory/<slug>.mdOne lesson per file, each carrying a Why: line. A lesson without a reason gets deleted by the next curation passone lesson each
memory/graveyard.md optionalRoutes tried and rejected, each with a mandatory expiry condition. Not a lesson, deliberately not index-linkedrows carry cause + expiry
memory/audit-log.jsonl optionalAppend-only score history from --log. Evidence, never an instructionnever pruned

The two-step save

Write memory/<slug>.md first, then append the one-line pointer to memory/index.md. Topic-file-first is deliberate: a crash between the two leaves an orphan, never a broken index. Link integrity is checked in both directions — dangling pointers and orphaned files both fail.

Index links are the one exception to the path convention. Everywhere else, paths are written relative to the project root. Link targets inside memory/index.md stay sibling-relative so the file reads standalone. The validator accepts both spellings.

Checks (7)

  • Memory index exists
  • Memory index is initialised and within its cap
  • Memory links intact (no dangling or orphaned entries)
  • Curation input exists (session journal)
  • Two-step save invariant documented
  • Curation cadence and human gate documented
  • Graveyard entries carry a cause and an expiry condition

10Curation — "dreaming"

Memory decays without maintenance. Curation runs between sessions, never during them, and proposes rather than applies.

Purpose

Find what the store should gain, merge or retire, using the journal as evidence — without letting an agent silently rewrite the rules it operates under.

Impacts / updates

Reads memory/journal.md, memory/index.md, the topic files and memory/graveyard.md. Writes only harness/dream-queue.md. It never edits memory/ and never touches AGENTS.md.

Why propose-never-apply

An agent that can silently rewrite its own operating rules has no reviewable history, and a proposal nobody accepted is indistinguishable from one that was. The queue is capped at 5 open proposals — volume is the proposer's problem, not the reviewer's.

The five signals

SignalCountable?What it means
Recurring but unrecordedyesA token recurs across dated journal entries with no lesson in the store
ReconsideredyesA graveyard route reappears — either its prohibition went unread, or its expiry quietly came true
ContradictionnoTwo lessons disagree; one must be demoted or superseded
Dead stocknoA lesson nothing has referenced. No read instrumentation exists, and building it is a documented non-goal
StalenoA lesson reality now contradicts — confidently wrong is worse than absent

The script counts the two countable signals and prints the other three as a checklist, rather than implying it found everything.

The dream queue's existence is deliberately unscored. A queue is the output of a curation pass, and curation runs every ~10 sessions — a young harness legitimately has none. Because enrich-harness acts only on failing checks, this also means a repair entry for the file would be unreachable code: an existence check would have to come first.

11Behavioral since v0.3.0

The structural systems say what to work on. This one governs how the code gets written. It owns no files — every check reads a section of AGENTS.md.

Purpose

Prevent the failure modes that pass every structural check: over-building, padded diffs, "done" before verification, and silently dropped safety.

Impacts / updates

Entirely embedded in AGENTS.md, so it competes with every other system for the same always-on context budget. Adding a section here costs tokens in every session forever — the argument for keeping each one short.

Components

PolicyWhat it constrains
Coding Policy — the ladderYAGNI → stdlib → native → existing dep → one line → minimum code. Stop at the first rung that holds.
Coding StandardsNo unrequested abstractions, no scaffolding for later, deletion over addition, mark deliberate shortcuts with a ponytail: comment
Editing DisciplineTouch only what the feature requires; match existing style; don't refactor what isn't broken
Definition of Done — test firstBugs: reproduction test first. Features: verification check first.
Before Multi-Step WorkA one-line success criterion, and a verify step per numbered step
Assumption surfacingState understanding in one line; stop and ask when the ambiguity is structural
Safety carve-outsNever simplify away: input validation at trust boundaries, error handling that prevents data loss, security, accessibility, hardware calibration
EscalationQuestion an over-specified spec rather than building it verbatim

Checks (8)

  • Coding minimalism policy (Ponytail ladder) present
  • Coding standards (no over-engineering) documented
  • Surgical editing discipline documented
  • Test-first verification gate present
  • Multi-step planning with verify-per-step documented
  • Proactive assumption surfacing documented
  • Safety carve-outs documented
  • Over-specified requirements escalation documented

12Tooling — the scripts

Node.js, standard library only, zero dependencies. None of them is copied into the target project.

ScriptPurposeTouches
create-harness.mjs Scaffolds a harness. Detects stack and package manager to build the verification commands. Skips existing files unless --force. writes the three root files, then everything under harness/. Resolves each destination through the layout detector, so re-running over a flat harness skips rather than duplicating.
validate-harness.mjs Scores the seven systems, names the bottleneck and anything else at or below 2. reads only — except --log, which appends to the audit log, and --html
enrich-harness.mjs Retrofits a harness that already exists: creates missing files from templates, splices missing sections into files already present. may write AGENTS.md sections · any missing scaffolded file. Acts only on failing checks.
curate-memory.mjs The dreaming pass. Counts two signals, prints three, proposes. writes harness/dream-queue.md only, and only with --apply
mutate-gate.mjs The adversary. Breaks init.sh or the project in known ways and reports what went unnoticed. writes a scratch copy only. Always exits 0 — a surviving mutant is a gap in the gate, not an error here.
run-benchmark.mjs Self-check (scaffold a throwaway harness and validate it), then score the target and eval coverage. writes harness/harness-benchmark.json · optional HTML
render-assessment-html.mjs Renders the assessment as a standalone HTML file. writes harness/harness-assessment.html
lib/harness-utils.mjs Shared: layout resolution, scoring, markdown-aware insertion, file IO, reporting. the single definition of the install layout

Thresholds that decide exit codes

run-benchmark.mjs gates on three numbers with defaults of 60, 80 and 90 — --min-score, --min-eval-score and --min-self-check-score. Set them explicitly in CI rather than inheriting a default that may change.

13Scoring model

Each system scores out of 5 by proportion of checks passed; the total is a percentage of 35.

SystemChecksWeight
instructions55 / 35
state55 / 35
verification85 / 35
scope65 / 35
lifecycle55 / 35
memory75 / 35
behavioral85 / 35

Every system is worth the same regardless of how many checks it contains. A system with 8 checks does not outrank one with 5 — each is 5 points. That keeps a well-instrumented area from masking a missing one.

Tiers

ScoreTierMeaning
≥ 85productionReady for multi-session agent work
≥ 85, weakest system ≤ 1usable ⚠One system entirely absent — fix it before multi-session work
≥ 60usableWorks for single sessions; gaps in handoff and state
≥ 30degradedBasic instructions, but the agent will drift across sessions
< 30insufficientNo reliable startup path

What the scoring deliberately does not do

  • The audit log is never wired to a check. A trend can say "this got worse"; it cannot say "this is unacceptable", because acceptable is contextual. Wire a trend to an exit code and the cheapest way to go green becomes "stop measuring honestly".
  • The context budget is advisory. There is no defensible universal ceiling, so it prints and never gates.
  • The mutation kill rate is opt-in. Measuring it copies the project and runs its gate once per mutation. Unmeasured, that check passes vacuously and the score is identical to what it was before the adversary existed.
Keyword checks are vocabulary-sensitive by design, and that has a sharp edge. A check that greps a file for a literal is satisfied by any occurrence — including a comment. Measured: a comment in init.sh explaining the fail-fast flag kept that check passing after the real line was deleted, so the mutation gate's drop-fail-fast probe survived. A self-check now forbids the literal appearing more than once in any shipped init.sh. Where possible, prefer a structural check — entrypointExecutesSomething() reads which lines are commands and cannot be satisfied by prose.

16Self-checks & known limits

The skill checks itself, because several defects here were invisible precisely because nothing failed.

Self-checks

FileGuards
scripts/insert-anchor.test.mjsMarkdown-aware section insertion: heading anchors insert after the section body, fenced code is not mistaken for headings, insertion happens once, a missing anchor is distinguishable from a no-op
scripts/index-coverage.test.mjsEvery index.md lists every file beside it; no links to missing files; the eval index matches evals.json; the documented score denominator matches SUBSYSTEMS; every .json template parses; no init.sh names the fail-fast flag twice; every init.sh reads the environment contract; the Required/Optional artifact groups match what the scorer enforces

Closed since v0.3.1

  • Memory and curation cases now exist in evals/evals.json — 19 evals, coverage 100/100.
  • Both bundled examples score 100/100 with memory: 5/5 and report production.
  • scripts/curate-memory.mjs ships — the two countable signals are automated, the three needing judgement print as a checklist.
  • enrich-harness.mjs inserted snippets immediately after the matched heading line rather than after the section body, pushing that section's own content below the inserted one. Insertion is now markdown- and fence-aware, inserts once, and reads the in-progress buffer so fixes in one run can anchor on sections added by earlier fixes.
  • Both examples' init.sh now read the environment contract, and templates/feature-list.schema.json parses as the JSON Schema its extension promises.

Still open

  • Keyword-based checks remain vocabulary-sensitive by design. Where a structural alternative exists it is preferred, but several checks still grep for prose.
  • Frontmatter timestamp / updated dates are hand-maintained and drift silently. A git-based check was considered and rejected: a directory rename touches every file without changing content, so the honest version costs more than the drift.
  • enrich-harness.mjs has no repair entry for harness/dream-queue.md — and cannot usefully have one until something scores the file's existence. See ch. 10.
